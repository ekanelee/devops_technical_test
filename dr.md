# Disaster Recovery Plan
 
This is how I would recover the application if something goes wrong. I have tried to be honest about two things: what is already protected by what I built, and what is only a plan. Where something is a plan, I say so.
 
The application is a PHP app (Nginx + PHP-FPM) on Cloud Run, with Cloud SQL (MySQL), a static-files bucket and a global load balancer, all defined in Terraform and deployed by GitHub Actions. Everything runs in `europe-west1`.
 
## What I am protecting and how
 
| Component | What can go wrong | Protected today | What I would add |
|---|---|---|---|
| Application code and images | Bad release, lost image | All code is in Git; images are tagged with the commit SHA, so any past version can be redeployed | Keep a copy of images in a second region |
| Cloud Run service | Bad revision, zone problem | Stateless, defined in Terraform, rebuilt from code at any time. Cloud Run spreads instances across zones by itself | Canary releases with traffic splitting |
| Cloud SQL | Data loss, corruption, zone outage | Automated daily backups and binary logs (point-in-time recovery) are on. Deletion protection is a variable (off in dev, on in prod). An HA (regional) instance is available through `db_high_availability` and is set to `true` in `prod.tfvars` | Cross-region read replica; tested restore drills |
| Static bucket | Objects deleted or overwritten | Files also live in Git and are re-uploaded by the pipeline on every deploy, so they can always be recreated | Object versioning and a dual-region location |
| Terraform state | Corrupted or deleted state | State bucket has versioning on, `prevent_destroy`, and keeps the 10 most recent old versions | Replicate the bucket to a second region |
| Secrets | Lost DB password | Generated by Terraform and stored in Secret Manager; it can be rotated by re-creating the random password | Rotation schedule |
| Whole project | Accidental deletion | Everything is code, so it can be recreated; the bootstrap layer rebuilds APIs, state bucket, registry and CI identity | Separate project for prod, organisation policies |
 
## Recovery objectives (my targets for production)
 
| | Target | Why |
|---|---|---|
| **RPO** (data I can afford to lose) | 5 minutes or less | Binary logs allow point-in-time recovery to nearly the moment of failure |
| **RTO** (time to be back) | 1 hour for most scenarios, 4 hours for a full region loss | Redeploying with Terraform is fast; the database restore is the slow part |
 
These are targets I would agree with the business, not guarantees. I have not measured them yet.
 
## Scenarios and runbooks
 
### 1. A bad release is deployed
 
Cloud Run keeps old revisions, and every image is tagged with its commit SHA.
 
1. Find the last good commit in Git or in the Actions tab.
2. Re-run the workflow of that commit from the Actions tab (it redeploys that SHA), or revert the bad commit and push to `main`.
3. Emergency option, when I need traffic back in seconds and will fix Terraform afterwards:
```bash
gcloud run revisions list --service app-dev --region europe-west1
gcloud run services update-traffic app-dev --region europe-west1 --to-revisions=<GOOD_REVISION>=100
```
   The next Terraform apply will overwrite this, so I follow it with step 2.
 
### 2. A zone becomes unavailable
 
Cloud Run reschedules instances in other zones automatically. Cloud SQL needs HA to survive this: with `db_high_availability = true` it fails over to the standby on its own (usually within a couple of minutes). With a single-zone instance (dev), I would restore from backup into another zone (scenario 4).
 
### 3. The whole region is unavailable (plan, not implemented)
 
1. Change `region` in the environment's tfvars to a second region (for example `europe-west9`) and create the Artifact Registry repository there through the bootstrap layer.
2. Promote the cross-region read replica of the database to primary, or restore the latest backup in the new region.
3. Build and push the images to the new registry (re-run the pipeline).
4. Run `terraform apply` for the new region. The load balancer keeps the same global design, and a new IP can be pointed at through DNS.
5. Verify with `./scripts/get-ip.sh <env>` and `curl <app_url>/readyz`.
The weak point is the database: without a replica, I can only recover to the last backup copy. That is why the replica is the first improvement on my list.
 
### 4. Database corrupted, or data deleted by mistake
 
Restore to a point just before the incident, into a new instance, so the damaged one is kept for investigation:
```bash
gcloud sql instances clone <SOURCE_INSTANCE> <NEW_INSTANCE> --point-in-time '2026-11-20T10:00:00Z'
gcloud sql backups list --instance <SOURCE_INSTANCE>
gcloud sql backups restore <BACKUP_ID> --restore-instance <INSTANCE>
```
Then I point the application at the new instance (new connection name through Terraform), check `/readyz`, and only then retire the old instance. Restoring a backup overwrites the target instance, so I prefer the clone.
 
### 5. Terraform state lost or corrupted
 
The state bucket is versioned, so I list the older versions and copy a good one back:
```bash
gcloud storage ls -a gs://<PROJECT_ID>-tfstate/envs/dev/
gcloud storage cp "gs://<PROJECT_ID>-tfstate/envs/dev/default.tfstate#<GENERATION>" gs://<PROJECT_ID>-tfstate/envs/dev/default.tfstate
terraform plan -var-file=environments/dev.tfvars
```
If a resource exists but the state forgot it, I use `terraform import` and re-check the plan until it shows no unexpected changes.
 
### 6. CI credentials may be compromised
 
There are no long-lived keys, which limits the damage. To be safe: disable the Workload Identity provider (or the `github-ci` service account), review the audit logs for the account, rotate any secrets, and re-enable access only after review. The provider only accepts tokens from this repository.
 
### 7. Everything is deleted (project wiped)
 
1. Create or restore the project and billing, authenticate with `gcloud`.
2. Re-run the bootstrap layer (APIs, state bucket, registry, CI identity).
3. Push images (pipeline) and apply Terraform.
4. Restore the database from the latest backup copy if one survives, or from an export kept elsewhere (a plan: scheduled exports to a bucket in another project).
## Testing the plan
 
A plan nobody has tested is a hope. My schedule would be: restore a backup into a scratch instance every quarter and time it, practise the rollback of scenario 1 on dev once a month, and run a yearly region-failover exercise on a copy of dev. After every drill I update this document with real timings.
 
## Limits of this plan
 
- Dev is single-zone with no HA and no replica, by design (cost).
- Region recovery depends on a replica that is not built yet.
- I have not run the restore commands against real backups; they come from the Google documentation and need a drill before I trust them.
- The DB password is stored in Terraform state, so protecting that bucket matters as much as protecting the database.
