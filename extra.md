# Extras: what I added beyond the assessment, and what I would do next
 
The brief gave me a clear list. While building it I made some choices that were not asked for, because I think they are what separates a working demo from something I would be comfortable running. This file lists them honestly, then the things I would add for a real production environment but did not have time to build.
 
## Part 1: What I added that was not in the brief
 
### Security and identity
- **Keyless CI authentication (Workload Identity Federation).** The brief suggested GitHub secrets for credentials. I avoided storing any Google key at all: GitHub gets a short-lived token per run, and only this repository can use it.
- **Dedicated runtime service account for Cloud Run**, with just two permissions (Cloud SQL client and access to one secret) instead of the broad default account.
- **Production database password generated by Terraform and stored in Secret Manager.** It never goes through GitHub, tfvars or the repository. The GitHub secrets I do use are only the identifiers WIF needs and a throwaway password for the test database.
- **Cloud Run closed to the internet.** Ingress accepts only traffic from the load balancer, so the `run.app` URL cannot be used to bypass the CDN or any future firewall. NB: I reverted this to allow incoming traffic so that ci smoke test and you the user can test it locally
- **Non-root containers** (PHP-FPM as `www-data`, `nginx-unprivileged`), and PHP-FPM configured so only `index.php` can ever be executed.
### Terraform and state
- **A bootstrap layer** that creates the APIs, the remote state bucket and the registry. It solves the chicken-and-egg problem of the state bucket, and it keeps state versioned, protected with `prevent_destroy`, and trimmed to the last 10 old versions.
- **One codebase for all environments.** Environment differences come from `dev.tfvars` / `prod.tfvars`, and each environment gets its own state file through a partial backend and `<env>.backend.hcl`. A `prod` configuration is defined (HA database, a warm instance, deletion protection) but I did not deploy it.
- **Input validation and descriptions** on variables, a `deletion_protection` switch (off in dev, on in prod), and a random suffix on the Cloud SQL name, because deleted instance names stay reserved.
- **Backups and point-in-time recovery** enabled on the database, and an HA switch (`db_high_availability`).
- **Artifact Registry instead of Google Container Registry**, because the latter has been shut down.
- **Cloud CDN** on the static-files backend bucket.
### Application and containers
- **Nginx as the ingress container with PHP-FPM as a sidecar** in a single Cloud Run service, with startup probes and container ordering.
- **Two kinds of health endpoints:** `/healthz` answered by Nginx alone (liveness) and `/readyz` that checks the database (readiness), so a database blip does not cause restart loops.
- **Multi-stage Docker build** so Composer and PHPUnit stay out of the runtime image.
- **`docker-compose.yml` that mirrors the Cloud Run layout** (Nginx shares PHP's network namespace). I used it to prove the app worked locally before touching GCP, which saved me a lot of time when billing was blocked.
- **PHP-FPM tuning that I can justify**: `clear_env = no` so environment variables reach PHP, a pool sized to the container's memory, and Cloud Run concurrency set close to the number of workers.
### CI/CD and quality
- **Terraform deploys the application.** The pipeline only changes the image tag, so there is no drift between the code and what runs, and the plan is saved and applied as a file.
- **Images tagged with the commit SHA**, never `latest`, so every deployment is traceable and a rollback is exact. Docker layer caching speeds up builds.
- **Tests with a real database:** unit tests, plus an integration test against a MySQL service container whose credentials come from a GitHub secret.
- **Terraform format and validate checks** on every run, and nothing is built or deployed unless tests pass.
- **A smoke test through the load balancer** after every deployment, with retries.
### Operations and developer experience
- **A Bash script with logging** that returns the load balancer IP for `dev` or `prod`. I explain in the README why that is the real public IP, since Cloud Run has none of its own.
- **`.gitattributes`** so script line endings stay Unix-style, and an ignore list for state files and credentials.
- **A written README with the difficulties I hit** (billing delay, the PHP-FPM startup probe, the 404 in the smoke test) and a troubleshooting table, plus `dr.md`.
## Part 2: What I would add for a production-ready environment
 
I did not build these, mostly for time. They are roughly in the order I would do them.
 
**Monitoring and alerting**
- Uptime checks on `/readyz` from several locations, defined in Terraform.
- Alert policies for the 5xx rate, latency, container restarts, and Cloud SQL CPU, disk and connections, sent to Slack or email.
- Structured JSON logging with log-based metrics, a dashboard, and agreed SLOs with error budgets.
**Security hardening**
- **Cloud Armor** on the backend service for rate limiting and basic OWASP rules.
- **Private Cloud SQL** (private IP with Cloud Run Direct VPC egress) so the database has no public address at all, and IAM database authentication so no password exists.
- HTTPS everywhere: a domain, a managed certificate, an HTTP-to-HTTPS redirect and HSTS.
- **Split CI identities:** a read-only one for planning on pull requests and a limited one for applying. Today the CI account has broad roles, which I accept only for this exercise.
- Vulnerability scanning of images (for example Trivy), static checks of Terraform (tflint, Checkov), Dependabot, and GitHub Actions pinned to commit SHAs.
- Image pinning by digest and Binary Authorization so only images built by the pipeline can run.
- Secret rotation, and organisation policies and audit log alerts.
**Delivery and reliability**
- Canary releases using Cloud Run traffic splitting, with automatic rollback when the smoke test or metrics fail.
- `terraform plan` posted as a comment on each pull request, and cost estimates (Infracost) in the same comment.
- Separate GCP projects per environment, with their own state and CI identities.
- Cross-region database replica, versioned and dual-region static bucket, and a rehearsed failover (see `dr.md`).
- Load testing to size the PHP-FPM pool and Cloud Run concurrency with real numbers instead of estimates, and a warm minimum of instances to avoid cold starts.
- Terraform tests for the modules, and budget alerts on the project.
## Part 3: Trade-offs I am aware of
 
- The production DB password is generated by Terraform, so it exists in the state file. I keep the bucket private and versioned, and the better answer is IAM authentication.
- The database has a public IP with no authorized networks, so only the Cloud SQL connector can connect. It is safe enough for a test, not my final design.
- The CI service account is powerful because Terraform manages many kinds of resources. I documented it instead of hiding it.
- Dev is single-zone and scales to zero to keep costs low, which means cold starts and no failover.
